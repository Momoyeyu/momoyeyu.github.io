# 前言

同时让 Agent 做几件事，很快会遇到两个矛盾：任务执行要能并行，任务之间又要保留必要的联系。塞进同一个会话，日志、文档和代码混在一起，长工具调用还会阻塞后续输入；分别开几个会话，谁负责什么、结果要转给谁，又全靠自己记。

DeepSeek Harness 团队在[《Super-agent 设计探索》](https://mp.weixin.qq.com/s/zoS7GlReWPhfCjENGxXCdg)中给出的答案是把会话管理从用户手里移到系统里，并提供了[开源原型](https://github.com/deepseek-ai/dsh-superagent-prototype)。本文按机制拆成六层：两层架构、事件路由、上下文管理、异步执行、运行环境，最后用原文的合成负载实验检验收益与代价。

# 两层架构

## Router 的职责边界

最直接的实现是两层：上层的 Router 对用户，下层的 Worker 对任务。下图画出一次并行请求的分工。

![Router 统一接收请求和回复，多个 Worker 在独立上下文里并行执行，状态与结果返回 Router](/img/posts/agent-super-agent/two-layer.svg)

左侧是用户入口：群聊、GitHub、邮件。请求只进 Router，由它分派任务；Worker A 排查登录故障，Worker B 更新部署文档，Worker C 整理技术资料，各自持有独立上下文和工具。回传给 Router 的只有状态与结果，执行过程留在各自会话里，Router 不需要逐行读 Worker 的日志。

这种分工成立，靠两条约束。**Router 不亲自执行具体任务**：如果它接到小修改就顺手打开终端，前台仍会被长命令占住，设计中甚至可以不给 Router 配 Bash。**Worker 不直接向用户发消息**：进展与结果先回 Router，由它结合其他任务统一回复，几个 Worker 同时完成时，群里不会出现几份互相缺少上下文的报告。

模型选择顺着这个分工来：Worker 处理复杂任务，用能力较强的模型；Router 只做短决策，可以尝试更快、更便宜的模型。前提是复杂分析确实在 Worker 一侧，如果让 Router 直接判断几个 PR 的方案冲突，它承担的就不再只是路由。

## 事件批处理

Worker 可以并行，Router 仍要逐个接收新事件，它会不会成为瓶颈？两个条件缓解了这个问题。Router 每次只做较短的决策，不输出长篇内容；一轮推理期间到达的事件可以排队，下一轮合并送入模型。

假设推理期间来了三个请求，逐条处理要三轮；合并后，模型在同一轮里分别决定它们的去向。输入变长会增加计算量，但三轮调用的固定开销不必完整付出三遍。

原文的压力测试给出了一组数字：待决策事件从每分钟 1 个增加到 40 个，平均批次从 1.0 增至 2.8，单次请求耗时只从 2.5 秒增至 3.9 秒。批次当然不能无限扩大，仍受上下文容量和多事件判断能力限制。结论是，在拆成多个 Router 之前，可以先看单个 Router 的批处理是否够用。

# 事件路由

## 准入与过滤

要持续跟进工作，输入不能只有用户消息。PR 有了新评论、CI 失败、群里补充了复现步骤，都可能意味着下一步该行动，这些输入统称为触发器（Trigger）。

收到消息不等于需要执行。群里的闲聊、重复通知远多于真正的工作请求，全部交给模型既慢又贵。分工是快慢两条路径：来源、群组、发送者这类稳定规则由代码检查，先筛掉明确无关的部分；「这条讨论是否已经需要修复代码」这类语义判断，再交给模型结合上下文决定。

## 订阅与直通

事件通过准入之后，要回答送给谁。同一个 PR 的评论、同一串群聊回复有天然的关联，系统把这样的事件流组织成 Thread，Worker 创建时订阅相关 Thread。下图画出完整流转。

![事件通过准入后查询订阅；已有任务走直通路径，新话题进入 Router 判断，再创建 Worker 和订阅](/img/posts/agent-super-agent/event-path.svg)

沿图走一遍：外部事件先过准入规则，不符合的直接忽略；通过的按 Thread ID 查询订阅。已有订阅时，事件直接送进对应 Worker，这条路径叫直通；没有订阅时才进入 Router，由它判断是否行动，需要行动就创建新 Worker 并建立 Thread 订阅。

继续看登录故障的例子。第一条问题报告到来时没有订阅者，走 Router 一侧创建任务；随后有人补充「只有 Safari 会白屏」，代码查到已有订阅，沿直通路径直接送给正在排查的 Worker，不必再让 Router 理解一次、转发一次。

订阅可以是多对多：一个 Worker 同时跟进群聊和 GitHub 上的 PR，一个 PR 也可以被修复与测试两个 Worker 共同订阅。它们会收到同一处的新消息，但订阅本身不解决代码冲突。图下方还有一条容易被忽略的注记：直通省的是重复路由，事件送达之后，操作仍要遵守权限规则。

## 主动介入时机

事件驱动还允许 Agent 在用户明确派单之前做准备。DeepSeek 团队举的例子是静默复现并修复：群里有人报告问题，Agent 先在后台尝试复现，确认问题存在并找到简单修法后才通知大家；尝试失败或没有值得交付的结果，就保持安静。

这里最影响体验的是出声时机。每条消息都回一句「正在检查」，只会把人的注意力拉回机器人。适合群聊的是简短结论和需要决定的问题，详细的变更与验证结果留在 PR 或文档里。

# 上下文管理

## 内联与溢出

事件找到了 Worker，还不能把相关内容全塞进上下文。一条 CI 结果可能带着几千行日志，全部注入很快占满窗口；只给一个 ID，模型又得反复调用工具才能拼出来龙去脉。下图给出折中方案。

![CI 事件在上下文中保留状态、失败摘要和关联 ID，完整日志存于窗口之外，按需通过 ID 读取](/img/posts/agent-super-agent/inline-spill.svg)

图左侧是 CI #318 的完整日志：数千行输出，失败的是 login.spec.ts，Safari 下超时。右侧把它拆成两部分：内联进当前上下文的只有失败摘要、关联的 PR #42 与 Worker W-3，以及指向完整输出的 log:318；完整日志溢出到外部记录，保留原文，需要时按 ID 读取指定片段。

选择哪些信息内联，依据是局部性：一条评论附近的回复、当前对象关联的 PR、同一任务最近的状态，比其他历史更可能用到。长内容达到预算上限就截断，并留下读取剩余部分的入口。目标不是一次给全，而是让模型能完成眼前的判断，同时知道缺的信息去哪找。

## 召回链

Router 长期运行，不可能把所有任务历史都留在窗口里。用户过几天问起之前的登录故障，需要一条找回去的路。给 Trigger、Thread、Worker 会话分配唯一 ID，并在对象里记录关联对象的 ID，就形成召回链。

![从当前消息沿 Thread 和 Worker 的关联找到修复 PR，每次读取只补充下一跳所需的信息](/img/posts/agent-super-agent/recall-chain.svg)

沿图走一遍：当前消息「登录问题好了吗？」指向 thread: T-812；Thread T-812 是登录故障讨论，指向 worker: W-3；Worker W-3 保存排查与修复记录，指向 pull_request: 42；最后读到 PR #42 的变更与 CI，拿到最新进展。每次读取一个对象，同时拿到下一跳的摘要与 ID，不必一开始就加载全部历史。

内联与溢出管的是现在放多少，召回链管的是移出窗口后还能找回来。链条依赖已经记录的关系，如果用户只说「上次那个问题」，而系统经历过好几个相似故障，仍然需要检索或追问；ID 能帮助找回对象，不能替用户补齐含糊的指代。

# 异步执行

单个 Worker 内部还有一种阻塞：测试要跑十分钟，期间用户又补充了要求。同步调用里，循环要等工具返回才能继续，新消息只能排队。下图对照两种调用方式的时间线。

![同步调用要等测试结束才能处理补充消息；异步调用在后台运行测试，期间可以处理新输入，完成结果再作为事件返回](/img/posts/agent-super-agent/duplex.svg)

左半边是同步 run()：调用之后等待工具返回，补充要求到达也只能排队。右半边是异步 start()：启动后立即返回，会话继续处理补充要求；工具在后台运行测试，完成时把结果作为新事件送回，再由会话接收。需要取消时调用 stop()。

例如测试刚开始，用户就说「先只检查 Safari」。采用异步执行后，Worker 可以在下一轮推理中看到这条消息，决定是否停止当前测试、缩小范围。它仍然要等正在进行的模型推理结束，但不用等整个测试跑完。

这种交互常被称为全双工：后台工作和新输入同时推进。两层架构解决任务之间的并行，异步工具解决任务内部的等待，两者配合，前台入口才不容易被长任务占住。

# 运行环境

要让 Agent 一直跟进任务，还得考虑机器休眠、进程重启。本地 Agent 通常把三样东西放在一起：运行推理和工具调度的循环、保存历史的会话状态、代码仓库和工具链所在的执行环境。它们不必待在同一个地方。

![云端分别运行 Agent 循环和保存会话状态，通过守护进程连接执行设备；独立看门狗检查运行状态与任务进展](/img/posts/agent-super-agent/separation.svg)

图上半部分是云端：Agent 循环跑在可替换的容器里，会话、事件、关联关系持久化保存，容器挂了换一个新的，从保存的状态恢复。下半部分是执行环境：本地 Mac、远程开发机、云端沙箱各装一个轻量守护进程，负责执行命令、传回工具结果。这就是自带机器（BYOM）的思路，因为未提交的代码、内部服务连接、特殊工具链都很难靠重新拉一份仓库来复制。

设备暂时离线时，云端仍能接收消息、保存进展、推进不依赖该设备的任务；需要读取本机未提交代码的操作，等它重新上线。把循环搬到云端，不意味着所有任务都能脱离执行环境。

图右上角的 Watchdog 是另一个独立会话，定期巡检两类问题：基础设施是否正常，任务是否取得进展。常规监控发现 API 错误、状态恢复失败，模型帮助判断任务有没有原地打转。测试环境暂时不可用时，重启 Worker 未必有用，看门狗可以继续等环境恢复再推动任务。恢复能力放在任务循环之外，是因为一个已经卡住的 Worker，不适合负责判断自己为什么卡住。

# 实验分析

原文用一组合成负载比较四种设计：每次运行约 300 条群聊和 CI 消息，其中约 20 条是工作请求；每种设计运行 5 次，消息间隔和工作时长压缩到原来的四分之一，模型调用耗时不变。编码工作由耗时工具模拟，因此这组实验主要观察调度效果，不代表真实编码质量。

![四种设计的完成时间对比，实心点为 p50，空心点为 p95；两层架构的完成时间更集中，关闭直通后变化很小](/img/posts/agent-super-agent/completion-time.svg)

| 设计 | p50，分钟 | p95，分钟 |
| --- | ---: | ---: |
| Super-agent | 12.4 | 15.7 |
| 关闭直通 | 12.6 | 15.5 |
| 单会话 + subagent，中性提示词 | 20.4 | 29.5 |
| 单会话 + subagent，优先委派 | 13.8 | 29.0 |

先看中位数与长尾的差别。单会话配备 subagent 工具，不代表模型会用：中性提示词下 5 次运行都没有委派，中位数 20.4 分钟；改成优先委派后，5 次中有 4 次委派，中位数降到 13.8 分钟，但仍有一次选择自行处理，p95 达到 29.0 分钟。提示词能换来并行收益，换不来稳定的分工。

两层架构的中位数为 12.4 分钟，p95 只有 15.7 分钟，四种设计里长尾最短。它的优势不主要来自单轮更快，而是每次运行都按同一条路径分派，完成时间更集中。

关闭直通后，完成时间几乎没变，中位数 12.6 分钟，但 Router 的决策次数增加约 30%，缓存读取量从 23.2M token 增至 31.8M token。说明这组负载下 Router 还没有成为瓶颈，直通的价值是减少额外调用和上下文读取，为更多事件留出容量，而不是直接缩短完成时间。

并行本身也有成本。Super-agent 的缓存读取量约为两种单会话配置的 2 到 4 倍，多个会话要分别维护和读取背景信息。这里统计的是缓存读取 token，不能直接当成总费用的倍数：需要及时反馈的交互任务，多用一些 token 可能值得；不着急的离线任务，则要重新算这笔账。

# 能力边界

两层结构让任务更容易同时推进，但任务常常会相互影响。三个 Worker 修改同一个模块，各自通过测试，不代表合起来正确。Router 可以识别这种关联，交给专门的 Worker 分析依赖和冲突；涉及需求取舍时仍需人做决定。并发增加以后，验证与验收可能成为新的瓶颈。

任务粒度也需要拿捏。很小的修改，新建 Worker、加载背景、回传结果的时间可能比修改本身还长；任务过大，进展又更难跟踪。这会影响任务如何合并、何时复用已有 Worker，需要根据实际工作分布调整。

另一个边界是信息和权限。个人或小团队可以共享一部分上下文，扩大到不同项目、不同组织后，就要决定哪些信息能共享、哪些必须隔离。外部事件只能提供任务线索，不能因为成功送达 Worker 就获得操作权限。尤其当云端循环连接着本地代码和凭据时，事件准入、执行授权和凭据隔离要各自做好。

# 结语

Super-agent 的核心，是把原本由用户承担的会话管理交给系统：Router 维护任务之间的联系，Worker 专注执行，订阅把后续消息送到负责的人，按需召回让历史不必一直占着窗口。

这些设计最终要改善的是一种具体的体验：交代几件事后可以离开一会儿，回来看到清楚的进展；需要决定的问题，Agent 能带着必要的信息来找我们。任务能开多少个只是开始，减少多少来回切换和重复说明，才更接近它的价值。
