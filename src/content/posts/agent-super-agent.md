# 前言

使用编程 Agent 时，我们通常会为每件事新开一个会话：一个修 bug，一个补测试，另一个帮忙查资料。单看每个会话，它们已经能完成不少工作；但同时开着几个，很快就需要自己记住谁在做什么、哪里卡住了、哪些结果要转给另一个会话。任务交给了 Agent，管理任务的工作仍然留在我们手里。

DeepSeek Harness 团队在《Super-agent 设计探索》中讨论的就是这个问题。他们提出**超级智能体**（Super-agent），希望让多个任务在后台持续推进，而用户始终只需要面对一个统一的入口。文章同时给出了一个[开源原型](https://github.com/deepseek-ai/dsh-superagent-prototype)，用于演示其中的部分设计。

这是 Agent 合集的第一篇。我们从会话为什么会成为负担讲起，再看 Router 与 Worker 如何分工，以及事件、上下文和执行环境怎样配合。理解这些之后，再回头看实验里多任务执行为什么变快，又付出了什么代价。

# 为什么要重新组织会话

会话最初是一个很自然的设计：用户给出问题，模型在同一段上下文里持续推理、调用工具，直到任务结束。问题、过程和结果都放在一起，单个任务很容易跟进。

但会话同时承担了两种职责：对模型来说，它管理上下文；对用户来说，它又成了管理任务的单位。这两件事在任务少的时候没有明显冲突，任务一多就开始互相牵制。

假设我们正在让 Agent 排查登录故障，又想让它更新文档。如果都放进同一个会话，排查日志和文档内容会混在一起；工具调用一旦长时间阻塞，后面的请求也只能等。分别开两个会话，可以让它们并行，但如果排查结果影响了文档，我们又得亲自搬运信息。

因此，这里需要解决的有两个问题：**任务执行要能并行，任务之间又要保留必要的联系。** 把所有内容塞进一个上下文，容易互相干扰；把上下文彻底拆开，协调成本又回到了用户身上。

Super-agent 的思路是把这两种职责分开。任务仍然可以在独立会话里执行，但由系统维护它们之间的关系、接收后续消息、汇总进展。用户可以在群聊里提出需求，稍后在另一个入口询问结果，不必先想起当时用了哪个会话。

这样一来，会话就逐渐退到后台。我们关心的是登录故障修好了没有，而不是应该去第几个聊天窗口里找答案。

# Router 与 Worker

## 交互和执行分开

最直接的实现是两层结构：上层的 **Router** 负责与用户交互、分派任务和跟踪整体进展；下层的 **Worker** 各自维护独立上下文，使用工具完成具体任务。

![Router 统一接收请求和回复，多个 Worker 在独立上下文里并行执行，状态与结果返回 Router](/img/posts/agent-super-agent/two-layer.svg)

例如，用户同时提出“修复登录故障”和“更新部署文档”，Router 分别交给两个 Worker。前者读取代码、复现问题、运行测试，后者查看部署配置、修改文档。它们的中间过程留在各自的上下文里，Router 只需要知道任务进展，以及是否有需要用户决定的事情。

这种分工能成立，有一个关键约束：**Router 不亲自执行具体任务。** 如果它接到一个小修改就顺手打开终端，前台仍然可能被长命令占住。设计中甚至可以不给 Router 配备 Bash，让执行工作始终落到 Worker 上。

Worker 则拥有完成任务所需的工具，但不直接向用户发消息。它把进展和结果交给 Router，由 Router 结合其他任务统一回复。这样，几个 Worker 同时完成工作时，群里也不会突然出现几份互相缺少上下文的报告。

模型的选择可以顺着这个分工来：Worker 需要处理复杂任务，通常使用能力较强的模型；Router 的工作较轻，可以尝试更快、更便宜的模型。前提是复杂分析确实交给了 Worker。如果让 Router 直接判断几个 PR 的方案冲突，它承担的工作就不再只是路由了。

## 一个 Router 能处理多少事

虽然 Worker 可以并行，Router 仍然要接收新请求。它会不会成为新的瓶颈？

首先，Router 每次只做较短的决策，通常不需要输出长篇内容。其次，一轮推理期间到达的事件可以先排队，在下一轮一起送入模型。因此，事件变多后不一定要按相同比例增加模型调用，系统会自然形成批处理。

这与逐条调用有明显区别。假设推理期间来了三个请求，逐条处理需要三轮；合并后，模型可以在同一轮里分别决定它们的去向。输入变长会增加计算量，但不必把三轮调用的开销完整付出三遍。

原文的压力测试中，待决策事件从每分钟 1 个增加到 40 个，平均批次从 1.0 增至 2.8，单次请求耗时只从 2.5 秒增至 3.9 秒。当然，批次也不能无限扩大，模型仍然受上下文容量和多事件判断能力限制。这个结果说明，在拆成多个 Router 之前，可以先看看一个 Router 的批处理能力是否已经够用。

# 让事件找到负责的任务

## 从提示词到事件

如果 Agent 只能等用户输入，它仍然需要人不断回来推动。要持续跟进工作，输入还得包括环境里的变化：PR 有了新评论、CI 失败、群里补充了复现步骤，都可能意味着下一步该行动了。这些输入统称为**触发器**（Trigger）。

不过，收到消息不等于需要执行任务。群里的闲聊、重复通知和无关 CI 结果远多于真正的工作请求，全部交给模型既慢又贵。这里可以先用代码筛掉明确无关的部分，例如检查来源、群组和发送者，再让模型结合上下文判断剩下的事件是否值得处理。

这就是快慢路径的分工：稳定、清楚的规则由代码执行；需要理解语义和上下文的判断交给模型。比如“只接收某个项目的事件”适合写成规则，“这条讨论是否已经需要修复代码”则更适合模型判断。

## Thread 与直通

接下来要解决的是，事件应该送给谁。

同一个 PR 下的评论、同一封邮件的往来、同一串群聊回复，都有天然的关联。系统把这样的事件流组织成 **Thread**。Router 创建任务时，让 Worker 订阅相关 Thread，此后的新事件就有了明确的接收者。

![事件通过准入后查询订阅；已有任务走直通路径，新话题进入 Router 判断，再创建 Worker 和订阅](/img/posts/agent-super-agent/event-path.svg)

继续看登录故障的例子。第一条问题报告到来时，还没有 Worker 负责，Router 创建任务并建立订阅。随后有人在同一讨论里补充“只有 Safari 会白屏”，代码查到订阅关系，直接把消息送给正在排查的 Worker，就不必再让 Router 理解一次、转发一次。

这种机制叫**直通**。它省掉了后续事件重复经过 Router 的开销，也让新的线索能及时进入任务上下文。只有没有订阅者、需要决定是否启动新任务的事件，才进入 Router 的决策路径。

订阅关系可以是多对多：一个 Worker 同时跟进群里的问题报告和 GitHub 上的 PR，一个 PR 也可以被修复与测试两个 Worker 共同订阅。它们会收到同一处的新消息，从而有机会发现彼此的变更；但订阅本身不会自动解决代码冲突，必要时仍要协调。

## 什么时候主动介入

事件驱动还允许 Agent 在用户明确派单之前做一些准备。例如收到会议邀请后，先检查日历冲突、整理背景、起草回复；最终是否发送，仍然可以留给用户决定。这相当于把可能会用到的工作提前做掉，减少人等待的时间。

DeepSeek 团队举的例子是“静默复现并修复”：群里有人报告问题，Agent 先在后台尝试复现，确认问题存在并找到简单修法后才通知大家。尝试失败或者没有值得交付的结果，就保持安静。

这里最影响体验的是出声的时机。每条消息都回复一句“正在检查”，只会把人的注意力重新拉回机器人身上。适合群聊的通常是简短结论和需要决定的问题；详细的变更与验证结果，则更适合留在 PR 或文档里。

# 上下文应该放多少

## 把窗口留给当前任务

事件找到了 Worker，还不能把相关内容一股脑塞进去。一条 CI 结果可能带着几千行日志，一次评审可能关联几十条评论。如果每次都完整注入，很快就会把上下文占满；如果只给一个 ID，模型又得不断调用工具，才能拼出事情的来龙去脉。

可以把上下文窗口看成一层缓存：近期很可能用到的信息直接放进去，完整记录保存在外部，需要时再取。这对应两个操作：**内联**把内容直接带进上下文，**溢出**把超出预算的内容留在外部，只保留引用。

![CI 事件在上下文中保留状态、失败摘要和关联 ID，完整日志存于窗口之外，按需通过 ID 读取](/img/posts/agent-super-agent/inline-spill.svg)

例如一次 CI 失败，注入内容可以包括失败的测试名、关键报错、所属 PR，以及完整日志的 ID。Worker 通常已经能据此决定下一步；如果关键报错不够，再读取相关日志片段。这样既省掉了第一次查找，也避免每次都携带整份日志。

选择哪些信息内联，可以参考局部性：一条评论附近的回复、当前对象关联的 PR、同一个任务最近的状态，往往比其他历史记录更可能用到。实现时先给 ID 和摘要，再逐步增加这些邻近信息；长内容达到预算上限后截断，并留下读取剩余部分的入口。

这里不必追求一次注入就给全。更实用的目标是让模型能完成眼前的判断，同时知道缺少的信息去哪里找。

## 沿着关联找回旧任务

Router 长期运行，也不可能把所有任务历史都留在窗口里。用户过几天问起之前的登录故障，它需要有办法重新找到当时的工作。

做法是给 Trigger、Thread 和 Worker 会话分配唯一 ID，并在对象里记录关联对象的 ID。例如，问题报告指向所属 Thread，Thread 指向处理它的 Worker，Worker 又关联修复 PR。读取一个对象时，工具同时返回下一步可能需要的摘要和 ID，就形成了一条**召回链**。

![从当前消息沿 Thread 和 Worker 的关联找到修复 PR，每次读取只补充下一跳所需的信息](/img/posts/agent-super-agent/recall-chain.svg)

于是，Router 不需要一直记住 PR 的全部内容，只要能找到当前问题对应的 Thread，就可以沿着这些关系读回进展。前面的内联与溢出控制“现在放多少”，召回链则保证“移出窗口后还能找回来”。

当然，链条依赖已经记录下来的关系。如果用户只说“上次那个问题”，系统又经历过好几个相似故障，仍然需要检索或追问。ID 能帮助找回对象，却不能替用户补齐含糊的指代。

# 工具在运行，消息也能继续

前面把任务拆到了多个 Worker，但单个 Worker 内部还有一个常见阻塞：测试要跑十分钟，期间用户又补充了要求。

在同步工具调用中，循环要等工具返回后才能继续。系统可以先把消息收进队列，但模型暂时看不到，自然也就无法根据新要求调整工作。

把长时间运行的工具改成异步调用，就能解除这个限制。模型调用 `start()` 后立即拿到任务已启动的响应，继续处理新消息；工具在后台完成时，再把结果作为新事件送回会话。需要取消时，则调用 `stop()`。

![同步调用要等测试结束才能处理补充消息；异步调用在后台运行测试，期间可以处理新输入，完成结果再作为事件返回](/img/posts/agent-super-agent/duplex.svg)

例如测试刚开始，用户就说“先只检查 Safari”。采用异步执行后，Worker 可以在下一轮推理中看到这条消息，决定是否停止当前测试、缩小范围。它仍然要等正在进行的模型推理结束，但不用等整个测试跑完。

这种交互常被称为**全双工**：后台工作和新输入可以同时推进。两层架构解决任务之间的并行，异步工具解决一个任务内部的等待，两者配合起来，前台入口才不容易被长任务占住。

# 怎样持续运行

## 循环、状态与执行环境

要让 Agent 一直跟进任务，还得考虑机器休眠、进程重启这些日常情况。一个本地 Agent 往往把三样东西放在一起：运行推理和工具调度的循环、保存历史的会话状态，以及代码仓库和工具链所在的执行环境。

它们其实不必待在同一个地方。循环可以放到云端运行，会话状态持久化到数据库，实际执行命令的环境则按任务需要连接。这样，负责运行循环的容器可以替换，任务历史也不会因为进程退出就一起丢失。

![云端分别运行 Agent 循环和保存会话状态，通过守护进程连接执行设备；独立看门狗检查运行状态与任务进展](/img/posts/agent-super-agent/separation.svg)

执行环境通常比循环更难迁移。本地可能有未提交的代码、内部服务连接，或者特殊工具链，简单地在云端重新拉一份仓库并不够。因此，设计中允许在原有机器上安装轻量守护进程，负责执行命令、传回结果。Agent 的循环在云端，具体工作仍能使用原来的环境，这就是**自带机器**（BYOM）的思路。

设备暂时离线时，云端仍然可以接收消息、保存任务进展、处理不依赖该设备的工作；需要读取那台机器上未提交代码的操作，则要等待它重新上线。把循环搬到云端，并不意味着所有任务都能脱离执行环境继续。

## 检查任务是否真的在推进

进程存活也不代表任务正常。Worker 可能反复遇到同一个错误，或者不断尝试，却始终没有接近目标。

为此，系统外部还可以运行一个独立的**看门狗**（Watchdog）会话，定期检查基础设施故障和 Worker 的进展。常规监控负责发现 API 错误、状态恢复失败等异常，模型则帮助判断任务有没有原地打转、是否偏离目标。

例如测试环境暂时不可用，重启 Worker 未必有用。看门狗可以继续检查外部环境，等它恢复后再推动任务。重点是把恢复能力放在任务循环之外，避免一个已经卡住的 Worker 还要负责判断自己为什么卡住。

# 实验里的收益与代价

原文用一组合成负载比较了四种设计：每次运行约 300 条群聊和 CI 消息，其中约 20 条是工作请求，其余包括闲聊、追问和取消。每种设计运行 5 次，消息间隔和工作时长压缩到原来的四分之一，模型调用耗时不变。编码工作由耗时工具模拟，因此这组实验主要观察调度效果。

![四种设计的完成时间对比，实心点为 p50，空心点为 p95；两层架构的完成时间更集中，关闭直通后变化很小](/img/posts/agent-super-agent/completion-time.svg)

单会话即使配备了 subagent 工具，也不一定会使用。采用中性提示词时，5 次运行都没有委派，所有任务留在主会话里执行，完成时间的中位数为 20.4 分钟。改成优先委派后，5 次中有 4 次委派，中位数降到 13.8 分钟，但仍有一次选择自行处理，p95 达到 29.0 分钟。

两层架构的中位数为 12.4 分钟，p95 为 15.7 分钟。它的优势来自分工更稳定：Router 始终把执行交给 Worker，任务之间的上下文也彼此隔离。依靠提示词同样能获得并行收益，但这组实验中，是否委派仍会受到模型当次判断的影响。

关闭直通后，完成时间几乎没变，Router 的决策次数却增加约 30%，缓存读取量从 23.2M token 增至 31.8M token。说明这组负载下 Router 还没有成为瓶颈，直通主要减少了额外调用和上下文读取，为更多事件留出容量。

并行本身也有成本。Super-agent 的缓存读取量约为两种单会话配置的 2 到 4 倍，多个会话需要分别维护和读取背景信息。这里统计的是缓存读取 token，不能直接当成总费用的倍数。对于需要及时反馈的交互任务，多用一些 token 可能值得；对于不着急的离线任务，就需要重新算这笔账。

# 还需要解决什么

两层结构让任务更容易同时推进，但真实工作里，任务常常会相互影响。如果三个 Worker 修改了同一个模块，它们各自通过测试，也不代表合起来就是正确的。Router 可以识别这种关联，再交给专门的 Worker 分析依赖和冲突；涉及需求取舍时，仍然需要人做决定。并发增加以后，验证与验收可能成为新的瓶颈。

任务粒度也需要拿捏。一个很小的修改，新建 Worker、加载背景、回传结果的时间可能比修改本身还长；任务过大，进展又更难跟踪。这会影响任务如何合并、何时复用已有 Worker，需要根据实际工作分布来调整。

另一个边界是信息和权限。个人或小团队可以共享一部分上下文，扩大到不同项目、不同组织后，就需要决定哪些信息能共享、哪些必须隔离。外部事件也只能提供任务线索，不能因为成功送达 Worker 就获得操作权限。尤其当云端循环连接着本地代码和凭据时，事件准入、执行授权和凭据隔离都要各自做好。

# 结语

Super-agent 的核心，是把原本由用户承担的会话管理交给系统：Router 维护任务之间的联系，Worker 专注执行，订阅把后续消息送到负责的人，按需召回让历史不必一直占着窗口。

这些设计最终要改善的是一种很具体的体验：交代几件事后，可以离开一会儿，回来看到清楚的进展；遇到需要决定的问题，Agent 能带着必要的信息来找我们。任务能开多少个只是开始，减少多少来回切换和重复说明，才更接近它的价值。
