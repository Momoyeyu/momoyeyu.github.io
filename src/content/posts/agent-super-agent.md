# 前言

下午四点，群里有人报了一个登录页白屏。你把它转给 Agent，它开了个会话去查。四点半产品经理在另一条消息里问进展，你先花两分钟想起这活派给了谁、查到哪一步。等把会话翻出来，发现它十分钟前就卡在一个过期的测试环境上了。

问题不在模型，也不在某个产品的实现。DeepSeek Harness 团队在《Super-agent 设计探索》里把它总结成一句话：单任务的上限取决于模型能力，多任务的上限取决于人的注意力。按他们的经验，一个人通常只能同时跟进 3 到 5 个活跃会话。

文章发布于 2026 年 10 月 31 日，同期在 GitHub 开源了配套原型 [dsh-superagent-prototype](https://github.com/deepseek-ai/dsh-superagent-prototype)，MIT 协议。作者在开头写了一句容易被跳过的话：本文讨论的是架构设计思路，并非对 DeepSeek Harness 现有功能的介绍。这句话决定了读法。它不是产品说明，而是一份系统设计文档，里面有一组只跑了合成负载的实验，和一个只实现了部分设计的原型。

下面按这个定位来读。先看它想解决什么，再逐层拆开 Router 与 Worker、事件通路、上下文预算、交互方式和部署形态，最后回到那组数字，说清哪些结论被支持，哪些还只是方向。文中会引用一份[二次解读](https://tt-a1i.github.io/agent-arch-share/)，凡是不属于原文的推演，我会明确标出。

这是 Agent 合集的第一篇。顺带说一句容易混的地方：这里的 Router 与 [MoE](../llm-moe/) 里的 Router 没有关系，后者在模型内部按 token 挑专家，前者在系统层面按事件挑任务。

# 为什么需要 Super-agent

编程 Agent 已经能自己完成不少工作。写代码、跑测试、翻日志、提 PR，这些事单拎出来都不太需要人盯着。但把几件事放在一起，问题就出现了。

现在的 Agent 以会话为基本单位，会话之间彼此隔离。你要同时推进三件事，就得开三个会话，并且自己记住哪个会话里装着哪条信息。会话这个设计其实同时干了两件事：它是模型上下文的管理单位，也是你管理任务的单位。第二件事不是模型需要的，是从 LLM API 那里顺手继承下来的。

会话内部还是串行的，这还在其次。更硬的问题是 ReAct 循环一次只能走一步，工具在跑，整个会话就停在那里。长任务一开，入口就被占住了，后面来的消息只能排队。

反过来，每件事各开一个会话，并行是有了，代价转到人身上。谁在做什么、哪件事有结果了、A 的结论要不要告诉 B，这些协调工作全由人来做。会话越多，切换成本越高，而人的注意力不会跟着变多。

所以 DeepSeek 的方案是把 Agent 与「人手动驱动的单个会话」解耦，让它成为一个跨会话保持上下文、同时推进多项任务而互不干扰的连续实体。他们给这种形态和它的系统架构起了个名字：超级智能体（Super-agent）。

目标被拆成四个特征：

- **连续**：在 IM 和 GitHub 之间来回，感觉始终是同一个 Agent，不用想「会话 X 里有没有信息 Y」。
- **高产**：长任务还在跑的时候，仍能接新的请求。
- **主动**：监听环境事件，值得处理就动手，其余时候保持安静。
- **持久**：一直在线，异常之后能自己恢复。

这四个词看起来只是产品愿望，实际上每个都对应一处架构改动。而且一个 ReAct 循环同时给不了它们：循环是串行的，没有跨会话记忆，不会自己醒来，也没法从自身之外观察自己。它们必须由循环之外的系统提供。

全文的支点是一句话：**会话应当是系统的实现细节，而不应成为用户的心智负担。**

一旦接受这条，后面几乎所有设计都变成推论。前台为什么可以不执行任务，Worker 为什么不能直接对人说话，事件为什么需要直通，上下文为什么必须按需内联，都能从这里推出来。

# 两层架构

要让系统接管会话管理，就绕不开一个权衡：连续性和吞吐量很难同时拿。

把所有事件都送进同一个会话，上下文最连续，什么都看得见。但循环一次推进一步，所有任务排成一队，速度受限于单个会话；不同任务的中间细节还挤在同一段上下文里，互相干扰，结果质量也下降。

反过来，每个事件新开一个会话，并发拉满，但任务之间不共享全局状态，结果容易脱节；而且每个会话都会自己去找用户回话，交互立刻变成一团乱麻。

两头都不行，只能分层。上层负责持续交互和全局协调，下层负责高并发执行。

![Router 只与人交互并派发完整任务，Worker 在隔离上下文中执行，结果统一由 Router 对外回复](/img/posts/agent-super-agent/two-layer.svg)

## 前台只派活

上层是 Router，长期存在的全局路由层。所有人机交互从各个入口进来，跨任务的信息和决策都汇聚在这里。它是全局的定序点、协调点和记忆中枢。

为了不变成瓶颈，Router 不亲自执行任务，只负责交互和分派。原文说它甚至可以完全不配备 Bash 工具。这句话不是限制，而是设计。一个没有 shell 的前台，只能用语言和工具调用去派活，不会顺手陷进某个具体任务里。

这里容易和 Agent Team 混起来。Agent Team 是把一个复杂任务拆成若干步，让各个角色分别承担，步骤之间耦合很紧，团队负责人得深入理解任务、规划子任务、频繁协调。Super-agent 的 Router 只分派完整任务，从高层跟踪任务之间的关系，不负责拆解单个任务。原文反过来也说了一句：Agent Team 完全可以按两层来做，用提示词约束主会话不亲自执行。

作者留了一句经验：Router 的工作通常比预想的更简单，用较轻量的模型往往就能兼顾速度和质量。这和 Worker 的选型正好相反。

## 后台只做任务

下层是 Worker，每个 Worker 拥有隔离的上下文和完整的工具集，专注一件事。任务的产出和代码质量由它决定，所以通常使用能力最强的模型。

Worker 有一条很强的约束：从不直接与人交互。它的推理过程和工具调用不进外部渠道，只把状态和结论汇报给 Router，由 Router 统一对外。这样并发是并发的，对外仍然只有一个声音。

Worker 之间通常不需要点对点通信。它们会在共享的工作环境里相遇，比如同一个 PR。只要相关 Worker 都订阅了这个 Thread，同一条新评论就会同时送到它们手上，冲突有机会被自行发现和处理。少数真的需要跨任务协调的情况，由 Router 转达。

## 批处理

> **Router 只有一个会话，为什么没有成为瓶颈？**

这是全文最反直觉的一段。

Router 内部不必只有一个会话，部分逻辑甚至完全不需要模型。作者选了最直接的做法：一个长期运行的 LLM 会话。他们发现它并不像想象中那样容易堵。

原因在排队。一轮推理正在进行时，新到的事件不会打断它，而是排在后面，等这一轮结束一起注入下一次调用。这自然形成了批处理。Router 每一步通常是长输入、短输出，合并进同一次调用的多个 Trigger 在预填充阶段并行计算，所以单次请求的耗时增长远低于批次大小的增长。

![事件在推理期间排队，下一轮合并成一批进入预填充，批次越大，每次决策分摊的推理时间越低](/img/posts/agent-super-agent/batching.svg)

原文在实验部分单独压了这一层：需要决策的事件从每分钟 1 个加到 40 个，平均批次从 1.0 涨到 2.8，单次请求从 2.5 秒涨到 3.9 秒，而每次决策的摊销推理时间从 6.4 秒降到 1.6 秒。越忙，单件事反而越便宜。

这个性质有上限，取决于上下文长度，以及模型一轮能准确处理多少个事件。但它解释了后面那个看似矛盾的现象：关掉直通机制后，Router 的决策次数和 token 消耗都明显上升，完成时间却几乎没有变化，因为单个 Router 还没有到顶。

真要扩展到单个会话装不下，Router 可以内部做多级过滤，或者水平分片成多个会话。但分片立刻回到同一个权衡：切得越细吞吐越高，各片共享的记忆越少。原文的判断是，在全局记忆问题解决之前，这个权衡会一直存在。

# 事件驱动

前面两节讲的是空间怎么分，这一节讲时间怎么触发。

单会话 Agent 的输入是人一条条敲进去的提示词。Super-agent 的主要输入换成了环境产生的半结构化事件，比如群消息、邮件、日历提醒、评审评论、CI 结果。原文把它们统称为触发器（Trigger）。

换成事件驱动，它才可能主动。但噪声也随之而来：真实群聊里绝大多数消息不需要 Agent 行动，真正该动手的很少。

## 两道过滤

> **每条群消息都要交给模型判断吗？**

不能，延迟和成本都受不了。这里借的是计算机系统里的快慢路径。模型推理灵活但昂贵，属于慢路径；高频、定义明确、规则稳定的判断写成确定性代码，属于快路径。

第一道是程序化策略。代码按事件来源、所属群组、发送者是否在允许名单里做准入。每个来源可以设成三种：仅响应明确请求、作为候选事件处理、忽略。绝大多数无关消息在这一步就被丢掉，模型根本没有被调用。

第二道是语义策略。通过准入的候选事件才交给模型，由它结合上下文和一段用提示词写的策略，判断是否行动。这一层同时是扩展点。想加一条规则，写一段自然语言就行，不用改代码。

![事件先过代码准入，未通过的直接丢弃；通过后按是否已有订阅者分流，有订阅者直通 Worker，没有才进入 Router 判断](/img/posts/agent-super-agent/event-path.svg)

## 订阅与直通

如果每个事件都要经过 Router，这个全局单点就会过载。所以快慢路径的划分也用在了路由上。

关键概念是 Thread：同一个 PR 里的连续评论、同一串群聊回复、同一封邮件往来，都构成一个事件流。

Router 为某个 Thread 的第一个事件创建 Worker 时，这个 Worker 直接订阅该 Thread。此后同一个 Thread 的新事件走两条路之一。

已经有订阅者，代码把它直接透传给订阅的 Worker，Router 不参与。这条路径省掉的是 Router 的一次判断和一次工具调用转发。还没有订阅者，Router 仍然看得到，由它判断要不要派活。

Thread 与 Worker 是多对多。一个 Worker 可以订阅多个相关 Thread，一个 Thread 也可以有多个 Worker 订阅。多个 Worker 在同一处相遇时，每个新事件同时直达所有订阅者，不需要两两通信，冲突就有机会被自己发现。

这里值得分清一件事：准入、路由、授权是三种不同的职责。直通只改变了消息怎么走，没有放宽谁能让它干活。二次解读的作者特意强调了这点，原文的授权模型写在配套文档里，阈值不在路由层。

## 推测执行

过滤器解决的是要不要看，推测执行解决的是要不要先做。

思路借自 CPU 的推测执行：在结果还不确定会被使用时，先在后台把工作做掉，有用的交付，没用的丢弃。人的等待次数和介入次数因此减少。

个人场景很好懂。收到会议邀请，后台先查日历冲突、收集背景、起草回复，人只需要看一眼再发。

团队场景的版本更有意思。他们在内部群里配了一条策略，叫静默复现并修复。有人报问题或者讨论改方案，Agent 先在后台尝试复现、寻找修复。只有确认问题确实存在、并且找到了简单的修法，它才出声；否则全程安静。

这个策略的赌注押在准确率上。误报一次，群里多一条噪音；误报几次，它就变成没人看的机器人。原文没有展开这层代价，但这是它能成立的隐含条件。

# 上下文的预算

事件被路由到某个会话之后，下一个问题是要往上下文窗口里放多少东西。

输入已经从有限几条人写的提示词，变成了持续产生的半结构化事件，注入设计的分量超过了写提示词。注入太多，窗口被填满，模型的注意力被稀释；注入太少，模型得反复调工具去读，执行步数暴涨。原文有一句话很到位：**浪费上下文窗口，就是浪费模型的智能。**

## 内联与溢出

他们把窗口当缓存用，注入归结为两种基本操作。内联是把近期可能用到的信息直接放进窗口，省掉一次工具往返；溢出是把超出预算或者很少使用的信息留在窗口外，窗口里只留一个引用或者摘要。

落地分三步，从少到多：

1. 只给当前对象的 ID 和一段摘要。
2. 按局部性逐层内联相关的信息。先加密切相关的对象 ID，再加空间或者时间上相邻的内容，比如正文的前 50 个字符、某条消息前后的几条消息、同一段评审讨论里相邻的评论。
3. 对超出较小上限的长内容做截断，留下指向剩余部分的指针，需要时再用工具读回来。

![上下文窗口像一层缓存，从摘要起步，按局部性逐层内联，超限内容截断后只在窗口里留指针](/img/posts/agent-super-agent/inline-spill.svg)

这几乎就是 CPU 缓存的工作方式。先给一个地址，命中就快，不命中再往下走一级。区别在于这里的局部性由对象的语义关系定义，而不是内存地址。

## 召回链

Router 自己也会遇到窗口问题。大量后续事件被直通给了 Worker，它长期运行，积累的历史任务装不下；可用户在另一个渠道提起旧事时，它又必须想起来。

把内联与溢出一致地用在每一类对象上，就得到了召回链。系统给 Trigger、Thread、Worker 会话都分配唯一 ID。注入某个对象时，顺带内联与之密切相关的对象 ID，这些 ID 把对象连成一张引用图。通过工具召回的每个对象，返回结果里同样内联下一跳的摘要和 ID。模型于是能从当前事件出发，一跳一跳往回找。

![从一条消息出发，沿内联的 ID 依次找回所属 Thread、处理过它的 Worker，以及该 Worker 关联的评审讨论](/img/posts/agent-super-agent/recall-chain.svg)

一个例子：当前消息属于 Thread #T-812，顺着内联的 ID 可以找到处理过它的 Worker W-3，再顺着 W-3 找到另一个代码评审 Thread，也就是那个 PR #42。

需要说清它的边界。引用图只连接系统经历过、并且被系统记下来的关系。二次解读的作者提醒得对：它不会自动建立所有跨渠道的关联。用户在私聊里问「上次那个登录问题怎么样了」，如果没有可用的关联，Router 仍然得靠检索、确认或者追问。召回链降低的是遗忘，不是消除歧义。

# 全双工

上下文就位，还有一处会卡住：一次工具调用要跑十分钟。

经典 ReAct 循环里，模型发起同步调用，循环就一直阻塞到工具返回。测试跑十分钟，这十分钟里会话收不进任何新输入，用户的消息只能排队。

要解开这个阻塞，对话得从轮流进行的半双工变成全双工。做法是把耗时的命令和工具调用换成异步的 `start()` 与 `stop()`。`start()` 立即返回 Started，循环不必等工具跑完；工具在后台结束后，系统以一条新的事件消息把结果投递给会话。模型也可以根据上下文调 `stop()`，终止跑得太久的命令。

这条改动的意义不只是快。前台对话和后台任务解耦之后，新输入只需要等当前这一步推理结束，而不必等工具执行完。异步任务机制在 DeepSeek Harness 里已经实现，原文交代了一句现状：它还没有默认启用。

![同步调用占住入口，start 立即返回，工具结果稍后作为一条新事件回到会话](/img/posts/agent-super-agent/duplex.svg)

## 按渠道说话

还剩一个更软的问题：在哪说，说多少。

群聊里要像同事一样，只在需要决策或者验收时通知人，只提直接明确的问题，给简短结论。他们验证过一条简单有效的硬规则：每次回复不超过 100 个词。

GitHub、邮件和文档这些异步渠道正好相反，要结构化、信息密度高。创建或者更新 PR 时按项目规范写清问题背景、变更说明和验证结果，邮件则直接成稿。

详细的推理过程和工具调用日志留在 Worker 内部，对外只由 Router 说话。这一点两层架构已经保证了，剩下的是按渠道定规范。

# 持续在线

前面几节都在讲单个实例内部怎么组织。要真的常驻，还得把运行位置从设备上挪走。

本地 Agent 把三件事绑在同一台机器上：跑循环的计算、要持久保存的会话状态，以及代码仓库和本地工具链这些执行环境。机器一休眠或者离线，三件事一起停。

## 计算与状态

第一刀切在计算和状态之间。跑 Agent 循环的计算本身可以是无状态的，真正需要留下的只有会话状态。于是循环放进可弹性伸缩的云容器，会话和其他持久状态进数据库。

这个切分看起来只是部署细节，实际改变了故障的含义。以前容器一挂，会话跟着消失，任务从头再来；现在容器只是一个可以随时替换的执行者，换一个接着读库里的状态就行。扩容、重启、灰度发布都不再需要保护某台具体的机器。

## 环境留在原处

第二刀更难。循环在云上，它怎么访问任务需要的执行环境？

有两种常见做法，都有代价。一是在云端起沙箱、拉代码、重建环境，可真实的工作环境里往往有没提交的本地改动、私有凭据、对内部服务的依赖、特定硬件或者工具链，同步成本高还容易漏。二是让人放弃本地环境，把工作整体搬上云，迁移成本对很多人来说不能接受。

作者的解法很简单：既然难搬的是环境本身，就别把它和循环一起搬走。云上只跑无状态的循环，负载重的执行环境留在原处，每个端点装一个轻量守护进程。守护进程不保存任何会话状态，只负责执行命令、把结果送回去。

这套做法和 Anthropic 在 [Decoupling the brain from the hands](https://www.anthropic.com/engineering/managed-agents) 里的思路一致：harness 保持无状态，会话日志存在框架之外，执行环境通过统一接口按需连接。区别在目标场景。Anthropic 讲的是托管服务和客户 VPC 里的按需沙箱，而这里首先得接上每个人日常使用的那台机器，上面有未提交的改动和本地凭据，还可能只是间歇性在线。所以他们把自带机器（BYOM）做成了一个正式选项。

![循环与状态在云端，执行环境留在原处；设备离线时，不依赖它的任务继续，依赖本地代码的操作等它回来](/img/posts/agent-super-agent/separation.svg)

效果是 Agent 不再绑在某台设备上，可以在不同执行设备之间切换。更能体现这个设计的是离线的情形：某台 Mac 下线了，云端照样接收消息、保存状态、推进不依赖那台机器的任务；依赖本地未提交代码的那些操作，则等设备重新连上再继续。二次解读把这个降级状态画得很清楚，也顺带纠正了一个容易产生的误解。其他可用的执行环境不会自动接手那台 Mac 上没同步的工作。

## 看门狗

> **进程还活着，任务就在推进吗？**

分布式系统长期运行，可靠性很难只靠内部逻辑维持，常规做法是在外面放一个控制循环。但智能体系统光看进程存活不够。很多异常不是崩溃：进程好好的，模型在原地打转，或者偏题了。

所以这里的看门狗是一个独立的智能体会话，跑在主系统之外，由定时消息驱动。它做三件事：处理 API 错误、状态恢复失败这类基础设施故障；用模型判断每个 Worker 是否真的取得了进展、有没有偏离目标；对暂时性的外部故障持续复查直到解决。

因为它本身是一个有完整工具集的会话，维护时可以直接用自然语言问它某个故障为什么发生，也可以在运行时让它纠正主系统的行为，比如增删提示词、调整触发规则。这比翻日志快得多。

![Watchdog 独立于主系统，定时巡检每个 Worker 的进展，不是只看进程是否存活](/img/posts/agent-super-agent/watchdog.svg)

二次解读给了一套干预顺序：先问它在干什么，再给恢复建议，然后重启任务，最后才找人。那是他们的实践建议。原文只写了职责，没有规定动作顺序。

# 实验证据

到这里，架构讲完了。原文给了一组实验，值得单独看，因为它的边界比结论更值得记住。

设置是这样的：四种设计同时跑，由一串群聊和 CI 消息驱动。每次运行约 300 条消息，其中约 20 条是工作请求，其余是闲聊、追问、取消请求和 CI 噪音。每种设计跑 5 次。消息间隔和工作时长都缩到原来的四分之一，模型调用耗时没有缩放。编码工作用一个只消耗时间的工具模拟。

最后一条最要紧。它衡量的是调度与协调能力，不是模型写代码的能力，所有关于快多少的结论都只在这个意义上成立。

## 四种设计

![四种设计的完成时间分布，每段横线从中位数延伸到 p95，长度就是长尾](/img/posts/agent-super-agent/completion-time.svg)

| 设计 | 完成时间 p50 | 完成时间 p95 | 缓存读取 token |
| --- | --- | --- | --- |
| Super-agent | 12.4 分钟 | 15.7 分钟 | 23.2M |
| Super-agent，关闭直通 | 12.6 分钟 | 15.5 分钟 | 31.8M |
| 单会话加 subagent 工具，中性提示词 | 20.4 分钟 | 29.5 分钟 | 6.1M |
| 单会话加 subagent 工具，优先委派提示词 | 13.8 分钟 | 29.0 分钟 | 10.8M |

超级智能体的中位数 12.4 分钟、p95 15.7 分钟。带 subagent 工具的单会话在中性提示词下是 20.4 和 29.5，慢了一大截，而且尾部很长。

原因不在模型，在提示词。中性提示词那一组，5 次运行里模型一次都没有调用子智能体，所有活都在主会话里做，一边做一边被新消息打断。

换成优先委派的提示词，5 次里有 4 次成功委派，中位数降到 13.8，但第 5 次模型判断这活很小，自己干了，长尾就留了下来，p95 仍然是 29.0。

也就是说，单会话能不能并行，取决于提示词写得好不好，以及模型当场的判断。这是概率性的。两层架构把它变成结构性约束：Router 不执行，Worker 只看自己订阅的 Thread。

## 直通的账

另一组对比更细：同样是两层架构，只把直通关掉。

关掉之后，Router 的决策次数增加约 30%，总缓存读取从 23.2M 涨到 31.8M，涨了约 37%，完成时间却几乎没动，p50 从 12.4 变成 12.6，p95 从 15.7 变成 15.5。

所以直通买到的不是速度，是余量。它省掉了每个后续事件都要经过前台的固定开销，而这组负载还没有把前台压满。真要压满，省下的就是吞吐量。

这也解释了批处理那条结论为什么成立。既然单个 Router 在每分钟 40 个事件下还能把摊销压到 1.6 秒，就没有必要为了吞吐过早分片，去换掉全局上下文的连续性。

## 代价

原文有一句很坦诚的话：相当于用 token 换取更短、更稳定的完成时间。

超级智能体的缓存读取是单会话设计的 2 到 4 倍。多个独立会话各自维护上下文，重复读的东西不会少。这笔账划不划算，取决于被省下的是什么。在人的等待和上下文切换比 token 贵得多的场景里，它划算；在批量、离线、成本敏感的场景里，它未必。

还有一层没法从这组数字里读出来。合成负载里没有真正困难的任务。真实任务会有依赖、会失败、需要回头改需求，这些都会放大协调成本，也会放大两层架构的好处。哪个方向占上风，原文没有回答。

# 没解决的问题

原文最后一节列了四类开放问题。它们不是一个层级的东西：有的缺工程方案，有的缺产品形态，有的缺安全前提。下面按重要性重排，并把二次解读里的推演并进来。

## 产出的上限

先把一个容易混的问题摆出来：并发数上去了，产出就一定上去吗？

二次解读里有一页专门问这个。九个 Agent 并行，不等于九倍产出。中间还有任务依赖，要等上游结果；还有冲突协调，要调整改法；还有结果验证，要检查质量、要返工。真正可用的产出，还得经过关键决策和人的确认。所以并发能力增强之后，瓶颈很可能只是从能不能同时做，移到协调、验证和验收。

这和原文的判断一致，只是原文用另一种方式说：进一步提升生产力的瓶颈正在转向人的注意力。

## 三个 PR 打架

一个具体的场景。三个 Worker 各自完成任务，却对同一个模块用了不同的方案，谁来协调？

二次解读给了三层处理。任务内的局部冲突，Worker 自己解决并报告影响。需要深入看几个 PR 的，Router 识别出来，交给一个专门的协调 Worker 去分析依赖和方案。涉及目标、授权或者重大取舍的，把证据和选项交给有权决定的人。

最后还有一句判断值得记：前台需要多强，取决于系统留给它多少判断。这句话其实在解释 Router 为什么能用轻模型。不是因为它只配做简单的事，而是因为设计上不让它承担需要深判断的事。一旦把协调压给它，轻模型就不够了。

## 派单的成本

另一个具体问题：一个两分钟的改动，值得新开一个 Worker 吗？

派给新会话，有固定开销：派单、加载背景、执行、汇报、转述，五步里只有一步是真正的修改。让主会话顺手做，省下交接，但可能占住入口，把后面的活堵住。

拆得太细，交接开销可能超过执行时间；拆得太粗，又更依赖 Worker 的规划能力和进度反馈。这个权衡原文没有给答案，它属于那种只能按任务分布来调的经验参数。

## 上下文边界

前面讨论的都是单个实例，默认它范围内的信息都汇到同一个全局上下文。

一旦使用范围从个人、小团队扩大，部署就变成了一件有语义的事：需要共享上下文的部分放同一个实例，需要隔离的部分各用独立实例。换句话说，怎么部署，就是在划上下文边界。

边界之间要协作，就是 A2A。原文明确说这里泛指智能体间通信，不是特指某个协议。各自代表不同权限边界、底层上下文又不共享的智能体之间怎么安全可靠地沟通，还没有答案。

## 安全

事件驱动让更多环境能驱动智能体，也让它接触到更多不可信输入。

原文点出一个隐含假设：云端跑循环、端点上装守护进程这套设计，默认云端和端点互相信任。可云端持续接收外部事件，端点握着私有代码、敏感数据和本地凭据。一旦服务端被入侵，或者循环被提示注入拿下，所有连着的端点都可能被接管。

就算云端从未被攻破，凭据也可能从正常执行路径里漏出去。只要凭据能进上下文，模型就有可能把它写出来。所以他们提出需要一种能用凭据、却永远看不到凭据的机制。这一点不解决，这套架构只能在很窄的可信范围里工作。

# 结语

这篇文章没有提出新理论。它做的事情是把计算机系统里几件老东西搬到了智能体系统上：缓存与局部性、快慢路径、推测执行、存算分离、外部控制循环。每一样都不新，组合起来才回答了那个具体问题：Agent 该怎么从你问它答，变成你派单它跟进。

最值得带走的不是 Router 和 Worker 这两个词，而是那条约束：会话是系统的实现细节。它把人的注意力从调度里解放出来，同时把调度的责任交给了系统。这也意味着系统要自己回答很多原本由人回答的问题，比如什么算进展、什么值得出声、什么时候该找人。

原文说，基于这套思路的实例已经在 DeepSeek Harness 内部持续运行，参与他们自己的开发。原型也开源了。下一步值得观察的不是它的 benchmark，而是它有没有真的减少人需要盯着的会话数。
